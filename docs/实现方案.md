# 纸上打飞机 · 飞牛（fnOS）联机对战应用 — 实现方案

> 目标：一个可安装在飞牛 NAS 上的应用，支持「双人对局 / 在线随机匹配 / 邀请码组队」，
> 服务端权威裁判（藏布阵），Go 单二进制实现。
> 本文是可行性研究 + 技术方案，不含完整代码，但关键设计给了可落地的结构与片段。

---

## 0. 结论先行

| 问题 | 结论 |
| --- | --- |
| 技术上可行吗 | **可行**。规则简单、状态极小（一盘 < 1KB），单核 NAS 跑几千场并发都够 |
| 飞牛能装吗 | **能**。官方 `fnpack` 提供 **Docker 模板**，产出 `.fpk`，装进应用中心；也支持统一网关 + WebSocket |
| 最大的技术难点 | 不是性能，是 **"藏布阵"的信息隔离** 和 **"死机残格骗人" 这类土规则的建模** |
| 最大的产品难点 | 朋友在**外网**怎么连到你家 NAS（公网/内网穿透），这决定联机体验 |
| 工作量（1 人） | MVP ≈ **10–13 人日**（约 2 周业余时间）；上架精品 ≈ 4 周 |

一句话架构：

```
浏览器 (PWA 单页)  ⇄ WebSocket ⇄  Go 单二进制（内嵌前端 + SQLite）
                                        ⇅
                              fnOS 统一网关(Unix Socket) / 独立端口 8080
```

## 1. 需求拆解

### 1.1 三种开局方式

| 模式 | 玩家路径 | 服务端要做的事 |
| --- | --- | --- |
| 双人房（邀请） | A 建房 → 得 6 位房间码/邀请链接 → B 打开链接进房 → 双方布阵 → 开始 | 房间生命周期、邀请码、可选密码、满员拒绝 |
| 随机匹配 | 点「快速开局」→ 进匹配池 → 配到对手 → 自动建房开局 | 匹配队列（等待时间/评分分段）、超时取消、断线重配 |
| 熟人房（口令） | 同一房间码 + 4 位口令 | 同上 + 口令校验、失败限流 |

### 1.2 对局内必须有的东西

- 布阵：10×10，3 架 1513 机型（1+5+1+3=10 格），**可四向旋转**，不可重叠 / 不可出界（可选「不可相邻」）
- 回合：喊号「字母+数字」（A–J 行 + 1–10 列，即 PDF 对战纸的坐标系）→ 应答 空 / 中 / 死
- 规则开关（对应纸上游戏的「土规则」，**必须做成房间级配置**）：
  - `ContinueOnHit`：打中是否连击（打中继续喊，打空换人）
  - `DeceptionOnDeadPlane`：飞机被打死后，残格是否继续答「中」骗对手
  - `KillByHeadOnly`：必须机头才算击落（否则机身打光也算）
  - `NoTouch`：飞机之间是否允许贴边相邻
- 超时：单步 30s、整局 30min，连续超时判负
- 断线重连：30s 宽限，回来推全量快照
- 结束：结算（用时/命中率/发数）+ 战绩入库 + 可选回放

### 1.3 明确不做（MVP 阶段）

注册邮箱验证、支付、观战、排行榜、2v2 双打、AI 对手（可后期加，规则引擎天然支持）。

## 2. 技术选型

| 层 | 选择 | 理由 |
| --- | --- | --- |
| 语言 | **Go 1.23+** | 单二进制、交叉编译无痛、NAS 上内存占用 < 50MB |
| HTTP/WS | `net/http` + `github.com/coder/websocket` | 标准库够用；coder/websocket 轻、支持 context 取消；`gorilla/websocket` 亦可 |
| 存储 | **SQLite**（`modernc.org/sqlite`，纯 Go 无 CGO） | 免运维、单文件、可备份；CGO_ENABLED=0 才好交叉编译到 ARM NAS |
| 前端 | 原生 JS + 少量 CSS（或 Vue 3 CDN/预构建）+ `//go:embed` | 不引入 Node 构建链，一个二进制带走全部资源 |
| 会话 | Cookie + 随机 token（服务端存 SQLite） | 比 JWT 更好吊销；游客也能有 token |
| 部署 | Docker（多阶段构建 → distroless/scratch）+ `fnpack` 打包 | 飞牛 Docker 模板原生支持；镜像 ≈ 20MB |

**为什么不用 boardgame.io / Colyseus / Node 方案**：它们要多跑一个 Node 进程、多一层构建链，在 NAS 上没必要；本项目状态机极简单，Go 手写房间 actor 更可控、更好测。

**为什么不用 Redis/Postgres**：单机 NAS 场景单实例足够。匹配队列用内存 + 定期落盘快照即可。留出 `Matcher` / `Store` 接口，将来要多实例再换 Redis，不动业务代码。

## 3. 总体架构

```
┌──────────────────────────── fnOS NAS ────────────────────────────┐
│  /var/apps/planeduel                                             │
│    ├─ target/  ← 二进制 + 内嵌前端 + app.sock（网关用）           │
│    ├─ etc/     ← 配置（TRIM_PKGETC）                              │
│    └─ var/     ← SQLite 数据（TRIM_PKGVAR）                       │
│                                                                  │
│   fnOS 统一网关 ──/app/planeduel──┐                              │
│                                   ├─→ Go 进程（同一套 handler）    │
│   端口服务  :8080  ───────────────┘                              │
│                                        │                         │
│   ┌────────────────────────────────────┴──────────────────┐      │
│   │ Hub（连接管理） → Matcher（匹配队列）                    │      │
│   │                 → RoomManager（房间 actor 池）           │      │
│   │                 → Store（SQLite：用户/战绩/回放）        │      │
│   └─────────────────────────────────────────────────────────┘    │
└──────────────────────────────────────────────────────────────────┘
        ↑ LAN 直连 IP:8080          ↑ 外网：Tunnel/frp/公网反代
```

要点：**同一套 HTTP handler 同时挂在 TCP 端口和 Unix Socket 上**，一份代码支持「网关访问」和「直连端口」两种入口（后面 8.3 给代码）。

## 4. 核心：规则引擎（纯函数，无 IO，最好写单测）

### 4.1 数据结构

```go
// 坐标：0..99，r=行(0..9 → A..J)，c=列(0..9 → 1..10)
type Cell uint8

type PlaneKind uint8
const (
    Kind1513 PlaneKind = iota // 机头1 + 机翅5 + 机身1 + 机尾3 = 10 格
)

// 1513 机型的 10 个偏移（基准朝向：机头朝上），坐标 (行, 列)
var shape1513 = [10][2]int{
    {0, 2},                          // 机头
    {1, 0}, {1, 1}, {1, 2}, {1, 3}, {1, 4}, // 机翅
    {2, 2},                          // 机身
    {3, 1}, {3, 2}, {3, 3},          // 机尾
}

type Plane struct {
    Head     Cell
    Cells    [10]Cell
    HitCount int
    Dead     bool
}

type Board struct {
    Rules      Rules
    Occ        [100]bool // 是否有格子
    PlaneOf    [100]int8 // 属于第几架（未占用填 -1）
    Head       [100]bool // 是否机头
    Planes     [3]Plane
    planeCount int
}
```

旋转只需要一个函数（包围盒 4 行 × 5 列，顺时针 90° 时 `new_r = c`、`new_c = 3 - r`）：

```go
func rotate(r, c, rot int) (int, int) {
    for i := 0; i < rot; i++ { // rot = 0..3 对应 0°/90°/180°/270°
        r, c = c, 3-r
    }
    return r, c
}
```

### 4.2 布阵校验（服务端必须做，别信前端）

```go
func (b *Board) Place(kind PlaneKind, anchor Cell, rot int) error {
    ar, ac := int(anchor)/10, int(anchor)%10
    var cells [10]Cell
    for i, off := range shape1513 {
        dr, dc := rotate(off[0], off[1], rot)
        r, c := ar+dr, ac+dc
        if r < 0 || r > 9 || c < 0 || c > 9 {
            return ErrOutOfBounds
        }
        cell := Cell(r*10 + c)
        if b.Occ[cell] {
            return ErrOverlap
        }
        cells[i] = cell
    }
    // 可选规则：飞机之间不得相邻（切比雪夫距离 ≤1 视为相邻）
    if b.Rules.NoTouch {
        for _, c := range cells {
            if b.neighborsOccupied(c) {
                return ErrTooClose
            }
        }
    }
    // 落子
    idx := b.planeCount
    for i, c := range cells {
        b.Occ[c] = true
        b.PlaneOf[c] = int8(idx)
        if i == 0 { b.Head[c] = true; b.Planes[idx].Head = c }
        b.Planes[idx].Cells[i] = c
    }
    b.planeCount++
    return nil
}
```

### 4.3 开火判定 —— 这里是全项目最容易写错的地方

难点在于「死机残格继续答中」这条土规则：**它不是让玩家撒谎，而是一种规则** —— 服务端完全能确定性算出该答什么，因此仍然可以做到权威裁判 + 双方信息一致。

```go
type Feedback uint8
const (
    Miss Feedback = iota // 空
    Hit                  // 中（含死机残格，若开着 Deception）
    Kill                 // 死（机头命中，该架报废）
)

func (m *Match) Fire(shooter int, c Cell) (Feedback, error) {
    if m.Turn != shooter {
        return 0, ErrNotYourTurn
    }
    if m.Shot[shooter].Has(c) { // 100 bit 的 bitset，O(1) 判重
        return 0, ErrRepeated
    }
    m.Shot[shooter].Set(c)
    target := m.Players[1-shooter]

    if !target.Board.Occ[c] {
        m.endTurn(shooter)                    // 打空 → 换人
        return Miss, nil
    }

    planeIdx := target.Board.PlaneOf[c]
    plane := &target.Planes[planeIdx]
    plane.HitCount++

    fb := Hit
    switch {
    case target.Board.Head[c]:
        // 打到机头：只有这架此前还活着，才算"死"
        if !plane.Dead {
            plane.Dead = true
            fb = Kill
        }
    case plane.Dead:
        // 已死的飞机：老实版答空，迷惑版继续答中
        if !m.Rules.DeceptionOnDeadPlane {
            fb = Miss
        }
    }

    // 非"只打机头"的规则：机身 9 格（机头以外的格）全中同样算击落
    if !plane.Dead && !m.Rules.KillByHeadOnly && plane.HitCount == 9 {
        plane.Dead = true
    }

    if m.Rules.ContinueOnHit && fb != Miss {
        // 连击：不换人
    } else {
        m.endTurn(shooter)
    }
    if m.allDead(target) { m.finish(1 - shooter) }
    return fb, nil
}
```

关键点：

1. **判重**用 100 bit 的 bitset（两个 `uint64`），O(1)，不用 map。
2. `plane.Dead` 与「机头是否被击中」是两个概念（`KillByHeadOnly=false` 时机身打光就死、机头可能还没中），结算要分清。
3. 胜负只看 `allDead`：三家 `Dead == true`。
4. **回放可复算**：存初始布阵 + 喊号序列，重放必须得到同一结果 → 天然防"事后改战绩"。

### 4.4 变体规则表（房间级）

```go
type Rules struct {
    Planes               int   // 3
    Kind                 PlaneKind
    AllowRotate          bool
    NoTouch              bool  // 飞机不可贴边相邻
    ContinueOnHit        bool  // 打中连击
    DeceptionOnDeadPlane bool  // 死机残格继续答"中"
    KillByHeadOnly       bool  // 必须机头才算击落
    ShotTimeoutSec       int   // 30
    MatchTimeoutSec      int   // 1800
}
func DefaultRules() Rules { /* 3 架、可旋转、连击开、迷惑开、机头击落 */ }
```

## 5. 通信协议（WebSocket，JSON）

统一信封，便于以后换 Proto/压缩：

```json
{ "t": "shot.fire", "id": 42, "d": { "cell": "C5" } }
```

请求带 `id`，响应回 `id`，同时广播 `evt`。

### 5.1 消息表

| 方向 | type | 说明 |
| --- | --- | --- |
| C→S | `hello` | 首次握手：`{token?, nick}`；返回用户信息 + 当前所在房间 |
| C→S | `room.create` | `{rules}` → 返回 `{code, link}` |
| C→S | `room.join` | `{code, pass?}` |
| C→S | `room.leave` | |
| C→S | `room.ready` | 布阵完成 → `{board: [[...]]}` 或 `{random:true}` |
| C→S | `queue.join` / `queue.leave` | 随机匹配 |
| C→S | `shot.fire` | `{cell:"C5"}` |
| C→S | `chat.send` | 房间内快捷短语（可关闭） |
| S→C | `queue.status` | `{pos, waitedSec, hint}` |
| S→C | `room.state` | 房间快照：玩家、规则、就绪状态 |
| S→C | `game.start` | 谁先手 |
| S→C | `game.snapshot` | 全量快照（重连/进场用），**只含自己的棋盘** |
| S→C | `game.event` | 逐步事件：`{by, cell, fb, turn, deadPlanes:[...]}` |
| S→C | `game.over` | `{winner, stats, matchId}` |
| S→C | `error` | `{code, msg}` |

### 5.2 「藏布阵」是硬约束

- 服务端**任何时候**都不下发对手的 `Board`；只下发「我打过的格子 + 反馈」。
- 自己的棋盘只回显自己的（用于布阵确认与残机提示）。
- 对手残机数：只能给「已确认击落数」，不能给「还有几架没露头」的隐含信息 —— 这个信息本身就是游戏的一部分，玩家自己记。

### 5.3 重连

- 连接建立即绑定 `userId`（来自 Cookie 或网关 Header），**绝不信任消息里的 userId**。
- 断线 → 房间内标记 `offline`，30s 宽限；重连后推 `game.snapshot`（含轮次、计时剩余）。
- 宽限超时：判负（或按配置改判「暂停等待」）。

## 6. 房间 actor（并发模型）

每个房间一个 goroutine + 一个 channel，**串行处理**所有事件，天然无锁、无竞态：

```go
type Room struct {
    id      string
    rules   Rules
    players [2]*Player
    match   *Match
    inbox   chan Event   // 所有输入都走这里
    ticker  *time.Ticker // 超时检查
}

func (r *Room) Run() {
    for {
        select {
        case ev := <-r.inbox:
            r.handle(ev)          // 单线程，放心改状态
            r.broadcast()
        case <-r.ticker.C:
            r.checkTimeouts()
        case <-r.done:
            return
        }
    }
}
```

- 扇出：`Hub` 维护 `roomID → *Room`、`conn → *Room` 映射。
- 单房间内存 < 2KB，1 万房间也就 20MB，NAS 完全无压力。

## 8. 飞牛 fnOS 落地（重点章节）

### 8.1 官方机制（已核对开发者文档）

- 应用包 = `.fpk`，用 **`fnpack`** 打包（当前 1.3.3，有 Windows/Linux/ARM/macOS 版）。
- `fnpack create planeduel --template docker` 会生成：`app/docker/docker-compose.yaml`、`cmd/` 生命周期脚本、`manifest`、`config/`、`wizard/`、图标。
- 安装后目录：`/var/apps/planeduel/{target,etc,var,tmp,home,cmd,config,wizard}`，脚本里用 `TRIM_APPDEST` / `TRIM_PKGETC` / `TRIM_PKGVAR`，**不要硬编码路径**。
- `manifest` 关键字段：`appname`、`version`、`display_name`、`desc`、`source=thirdparty`、`platform`、`os_min_version`、`service_port`、`checkport`、`ctl_stop`、`install_dep_apps`。
- **统一网关**：`app/ui/config` 里声明 `gatewayPrefix: /app/planeduel` + `gatewaySocket: app.sock`，服务监听 `${TRIM_APPDEST}/app.sock`，飞牛校验登录后转发，并附带 `X-Trim-Userid` / `X-Trim-Username` / `X-Trim-Isadmin`。**官方明确支持 WebSocket**（建议放子路径 `/app/planeduel/ws`）。
- 运行时环境（Python/Node/Java）靠 `install_dep_apps` 拉取 —— **我们用不上，Go 单二进制自带一切**，这是 Go 方案在飞牛上的最大优势。

### 8.2 manifest 示例

```ini
appname=planeduel
version=0.1.0
display_name=纸上打飞机
desc=双人/随机/邀请开局的纸上打飞机对战，服务端裁判、断线可续。
source=thirdparty
platform=all
maintainer=your name
os_min_version=1.2.0
service_port=8080
checkport=true
ctl_stop=true
```

### 8.3 一份代码挂两个入口（TCP + 网关 Unix Socket）

```go
func main() {
    mux := buildRouter()            // /healthz /api/* /ws /(静态)

    // 入口 1：独立端口（局域网/外网/游客可直达）
    go func() {
        log.Fatal(http.ListenAndServe(":8080", mux))
    }()

    // 入口 2：飞牛统一网关（仅当部署在 fnOS 上）
    if dest := os.Getenv("TRIM_APPDEST"); dest != "" {
        sock := filepath.Join(dest, "app.sock")
        _ = os.Remove(sock)
        ln, err := net.Listen("unix", sock)
        if err != nil { log.Fatalf("unix listen: %v", err) }
        _ = os.Chmod(sock, 0660)
        log.Fatal(http.Serve(ln, mux))
    }
}
```

网关进来的请求带 `X-Trim-Userid`，我们把它映射成本地用户（首次自动建号）——**等于白送一套 NAS 账号体系**，省掉注册/找回密码。

### 8.5 浏览器缓存坑（必看）

网关下所有请求都在 `/app/planeduel` 前缀内，静态资源要用**相对路径**（`./app.js`）或按 `base` 生成；否则变成 `/app.js` 直接 404。

注意：**`CGO_ENABLED=0`**（SQLite 用纯 Go 驱动）+ `buildx --platform linux/amd64,linux/arm64`（飞牛设备有 x86 也有 ARM）。

### 8.9 外网联机（真正决定体验的一步）

| 方案 | 适用 | 说明 |
| --- | --- | --- |
| 局域网直连 | 家人/同事 | `http://NAS_IP:8080`，零配置 |
| 飞牛统一网关 + 远程访问 | 已开远程访问的飞牛用户 | 走 fnOS 域名，需对方有飞牛账号 |
| Cloudflare Tunnel | 想给朋友发链接 | 免费、自动 HTTPS、WS 支持好；把 `/ws` 的 read timeout 调大 |

## 9. 数据模型（SQLite）

```sql
PRAGMA journal_mode=WAL;

CREATE TABLE users (
  id         INTEGER PRIMARY KEY,
  name       TEXT UNIQUE NOT NULL,
  is_guest   INTEGER NOT NULL DEFAULT 1,
  fnos_uid   INTEGER UNIQUE,          -- 网关透传的 UID（可空）
  rating     INTEGER NOT NULL DEFAULT 1000,
  created_at INTEGER NOT NULL
);

CREATE TABLE matches (
  id          TEXT PRIMARY KEY,        -- ULID
  rules_json  TEXT NOT NULL,
  p1, p2      INTEGER NOT NULL REFERENCES users(id),
  winner      INTEGER,                 -- NULL=未结束
  board1      BLOB NOT NULL,           -- 布阵（30 字节 bitset）
  board2      BLOB NOT NULL,
  moves       BLOB NOT NULL,           -- 喊号序列（每步 1 字节 + 反馈 1 字节）
  started_at  INTEGER NOT NULL,
  ended_at    INTEGER
);

CREATE TABLE sessions (
  token      TEXT PRIMARY KEY,
  user_id    INTEGER NOT NULL,
  expires_at INTEGER NOT NULL
);
CREATE INDEX idx_sessions_user ON sessions(user_id);
```

- 一局 `moves` 最多 200 字节，历史全存也无压力（10 万局 ≈ 20MB）。
- 回放 = 重放 `board + moves`，结果必须一致（可做一致性自检）。

## 10. 反作弊与稳定性

| 风险 | 措施 |
| --- | --- |
| 客户端偷看对手布阵 | 服务端永不下发；DTO 白名单构造，禁止直接序列化内部结构 |
| 伪造身份 | 连接绑定 Cookie/网关 Header，消息里的 `userId` 一律忽略 |
| 刷接口 | 每连接令牌桶（如 5 msg/s），超限断开；房间创建按 IP 限流 |
| 篡改胜负 | 服务端权威 + 回放复算 + `board` 校验和 |
| 慢速攻击/僵尸连接 | ping/pong 20s，读写超时 60s；空房间 2h GC |
| NAS 断电 | WAL + 每次 `game.event` 后异步落盘（单写者 goroutine）；启动时恢复未完成房间（或判负退款式结算） |
| 内存泄漏 | 房间结束必须 `close(done)`，Hub 反注册；`go test -race` |

## 14. 已确认的决策（v0.2）

### 14.1 入口：统一网关为主 + 可选的独立端口（面板开关）

- **始终开启**：飞牛统一网关 `/app/planeduel`（部署在 fnOS 上时自动监听 `$TRIM_APPDEST/app.sock`）。
- **始终开启（本机）**：`127.0.0.1:8081` 回环管理入口。这不是凑数：端口默认关闭时，若无此入口就**没有任何地方能打开设置面板**（死锁）；同时它还是网关故障时的恢复通道。仅绑定回环，不对外。
- **可选开启**：`0.0.0.0:<public_port>`，默认关闭，可在设置面板**热开关**，无需重启进程。

API：

```http
GET  /api/admin/settings          → {public_port_enabled, public_port, status:{listening, addr, error}, gateway_mode}
PUT  /api/admin/settings  {"public_port_enabled": true, "public_port": 18080}
```

鉴权：飞牛网关注入的 `X-Trim-Isadmin: true`，或本地 `X-Admin-Token`（启动日志打印、落盘在 `config.json`）。

实现要点（`internal/app/port.go`）——`PortManager` 持锁管理 `net.Listener` + `http.Server`，`Apply()` 幂等：开关不变直接返回，变则先 `Close()` 旧监听再 `net.Listen()` 新端口；失败时把错误写进 `status.error` 回显给面板，配置仍保留（下次启动会再试）。

### 14.2 身份：纯游客昵称，全局唯一

| 规则 | 取值 |
| --- | --- |
| 长度 | 2–12 个字符（按 rune 计，中文算 1 个） |
| 允许字符 | 中文、英文字母、数字、`_`、`-` |
| 归一化 | 去首尾空格 + 转小写后判重（`XiaoMing` 与 `xiaoming` 视为冲突） |
| 保留词 | admin / root / system / 管理员 / 系统 / 官方 / 客服 / 匿名 / 游客 |
| 占用释放 | 30 天不活跃自动释放（`nick_ttl_days` 可配） |
| 认人方式 | HttpOnly Cookie `pd_sid`（随机 32 字节），180 天有效 |

- 冲突返回 **409**，前端提示「换一个」；非法昵称返回 400。
- 昵称与 token 分离：改昵称不会换身份（同一 token 可以改名），避免「换个名字就变成另一个人」。
- 全局唯一是刻意的：NAS 是熟人环境，重名会直接毁掉对局识别（谁打谁）。代价是昵称空间有限，所以必须带 TTL 释放。

### 14.3 与「服务端权威」的配合

- 昵称只用于**展示与匹配**，所有权限判断走 token / 网关 Header。
- 任何消息里客户端自报的 `userId` / `nick` 一律不采信（网关文档也明确要求这一点）。
